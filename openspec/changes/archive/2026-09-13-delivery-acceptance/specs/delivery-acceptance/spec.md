# Delta Spec: delivery-acceptance

## Purpose

把"执行结束"与"交付正确"分开：宿主声明的确定性业务检查在成功提交前必经，失败产出结构化缺口并允许一次受控修正，验收结论独立于执行状态持久化——堵住"结构合格即交付"的错误放行（冻结样本 8/18、留出集 15/29 的实测放行率）。

## ADDED Requirements

### Requirement: 宿主注册检查器与任务级声明

内核 SHALL 提供检查器注册协议：宿主按 `(id, version)` 注册同步纯函数检查器（输入为候选交付与任务声明的参数，输出为通过/失败与结构化发现），并在注册时申报预期执行时长；内核 MUST NOT 内置或从任务名称推断任何业务规则。任务声明 MUST 固定检查器版本（`checker_id + checker_version`），版本纳入声明指纹；派发前 MUST 校验声明的 `(id, version)` 已注册，缺失 MUST 响亮拒绝。**崩溃恢复中声明版本已不可用（宿主升级且未保留旧版本）时，处置 MUST 按验收模式分档**：off 模式不执行验收、不影响原交付流程；shadow 模式该检查记录 unverified 但不改变交付决策；required 模式该检查判 unverified，必需检查任务 MUST NOT 落成功终态。检查器 MUST 在隔离的守护线程中执行：在飞检查线程数有硬上限（达限即对新检查判 unverified，不排队），超时 MUST 判 unverified 并将检查器标记 degraded（后续调用直接 unverified）、迟到结果 MUST 丢弃；单个阻塞检查器 MUST NOT 使其他健康检查器不可用，也 MUST NOT 阻止进程正常退出。内核不承诺回收被阻塞的检查线程（契约要求检查器时间有界，超时兜底以 unverified 计）。未声明任何检查的任务、或验收模式为 off 时，MUST 保持现有交付行为与成本零变化。

#### Scenario: 声明随创建事件持久化并恢复可用
- **WHEN** 一个声明了检查（含检查器版本）的任务被派发并落盘，进程重启后恢复
- **THEN** 恢复出的任务仍携带完整检查声明与版本

#### Scenario: 未注册或版本缺失的声明被响亮拒绝
- **WHEN** 任务声明引用的 `(checker_id, checker_version)` 未在宿主注册
- **THEN** 派发前返回明确错误，任务不进入执行

#### Scenario: 恢复中版本缺失按模式分档处置
- **WHEN** 恢复的存量任务声明的检查器版本在当前宿主注册表中不存在
- **THEN** off 模式下验收不执行、交付流程不受影响；shadow 模式下该检查记录 unverified 且交付决策不变；required 模式下该检查判 unverified 且（若为必需检查）任务不得落成功终态

#### Scenario: 阻塞检查器不影响健康检查器与退出
- **WHEN** 一个必需检查器无限阻塞进入 degraded，随后另一健康检查器执行，最后关闭 runtime
- **THEN** 健康检查器正常执行并返回结论（不被排队拖垮），进程可正常退出（守护线程不阻止关闭）

#### Scenario: 未声明任何检查的任务零行为变化
- **WHEN** 任务未声明任何检查（必需或提示性）
- **THEN** 交付路径、事件与成本与改造前完全一致

### Requirement: 候选结构与全路径提交边界

验收的候选 MUST 是**分开的交付二元组**（最终正文与摘要各自独立字段），检查、指纹计算与最终提交 MUST 使用同一份候选；MUST NOT 以正文与摘要拼接后的单串作为检查对象。**验收模式为 required 时**，携带必需检查的任务 MUST 经全部必需检查（先结构、后领域）通过后才落定成功交付；shadow 模式执行并记录但不改变交付决策，off 模式不执行（见行为矩阵 requirement）。以下每条**以任务收尾为形态**的成功提交路径在 required 模式下都 MUST 经过该验收边界：经 `finish_task` 的收尾、observe 判成功的收尾 run、父任务对子任务结果的接收（子任务自身的验收状态随结果上抛）、`run_single_task` 兼容入口。**交互任务的中间交流回合（park 让位用户的纯文本）不是交付候选**：不触发必需验收、不产生验收记录；声明了必需检查的交互任务，其最终交付 MUST 以收尾 run（如 `finish_task`）为形态并经验收。required 模式下候选未通过必需检查时，任务 MUST NOT 落成功终态。流式过程文本不受影响；已展示文本不承诺事后撤回。

#### Scenario: 摘要附着不污染结构检查
- **WHEN** 最终正文是合法 JSON、自评摘要附着其上，结构检查按声明解析正文
- **THEN** 检查对象是分开的正文字段，摘要不参与正文的结构判定

#### Scenario: finish_task 收尾必经验收
- **WHEN** 携带必需检查的任务经 finish_task 收尾、候选未通过领域检查
- **THEN** 任务不落成功终态，进入缺口反馈路径

#### Scenario: 交互中间交流不触发验收
- **WHEN** 交互任务在对话中途以纯文本让位用户（park）
- **THEN** 该回合不产生验收记录、不影响修正额度；其最终交付以收尾 run 为候选受验

#### Scenario: 交互最终答复经收尾验收
- **WHEN** 声明必需检查的交互任务以 finish_task 收尾、候选未通过必需检查
- **THEN** 该最终答复不被提交为已验收交付，缺口反馈生效

#### Scenario: 子任务结果上抛前经验收
- **WHEN** 携带必需检查的子任务完成、结果将被父任务接收
- **THEN** 父任务只接收带验收状态标注（通过/失败/未验证）的结果，未通过者带缺口上抛

#### Scenario: 兼容入口实际完成一次修正
- **WHEN** `run_single_task` 入口的任务首次必需检查失败且预算允许
- **THEN** 该入口内联发起恰好一次修正生成并重跑检查，向调用方返回修正后的最终结果

### Requirement: 结构化缺口与一次受控修正（跨崩溃额度保证）

检查失败 MUST 产出结构化缺口事实：失败条件、涉及字段或记录、依据的数据引用、可修正建议——不使用无定位的泛化失败文案。修正额度 MUST 以**预占事件先于修正生成落盘**的方式持久化：预占（额度计数增加、任务回排）成功后才允许发起修正生成；重启 MUST NOT 重置或增加修正额度，全程每任务至多一次修正。预占后、生成前崩溃的任务，恢复续跑视为完成该次已预占的修正（计数不再增加）。确认为答复错误且预算允许时执行修正：缺口注入下一轮生成，修正后 MUST **重跑全部必需检查**。出现以下任一情形时 MUST 终止自动修正并保留候选与未解决项：缺口与上次完全相同且无新证据、修正额度已耗尽、预算不足、检查器 degraded 或故障。修正相关的模型调用 MUST 计入任务成本并受现有执行预算约束。

#### Scenario: 一次修正后全量复检
- **WHEN** 候选首次未通过，修正额度为 1
- **THEN** 恰好触发一轮修正，且修正产物重跑全部必需检查后才可能落定成功

#### Scenario: 修正引入的新损坏被复检拦截
- **WHEN** 修正修复了原缺口但破坏了另一必需检查项
- **THEN** 复检失败，整体不落成功终态

#### Scenario: 重复缺口终止自动修正
- **WHEN** 修正后的候选产生与上一轮完全相同的缺口
- **THEN** 不再触发第二次修正，任务带着候选与未解决缺口走失败路径

#### Scenario: 预算不足时不修正
- **WHEN** 任务执行预算已耗尽而候选未通过必需检查
- **THEN** 不发起修正，直接进入验收失败处置

#### Scenario: 预占先于生成落盘
- **WHEN** 修正额度预占与修正生成之间发生崩溃
- **THEN** 恢复后额度计数已持久化，不因重启获得额外修正机会

#### Scenario: 预占后生成前崩溃的续跑语义
- **WHEN** 预占事件已落盘、修正 run 尚未开始时进程崩溃
- **THEN** 恢复续跑完成该次已预占的修正（计数不变），续跑候选仍失败则落失败终态

### Requirement: 验收状态独立于执行状态

验收结论 SHALL 以 `passed / failed / unverified` 三态独立表达，MUST NOT 复用或改写 Task.status 的语义。检查器异常、超时或能力未覆盖 MUST 产生 `unverified`，绝不产生 `passed`。required 模式下必需检查未通过的任务 MUST NOT 被提交为"已验证成功"；提示性（非必需）检查失败 MUST NOT 阻塞交付。验收结论 MUST 绑定**输出指纹、输入快照标识、检查声明版本**三元组——三者任一变化，旧结论 MUST NOT 用于证明新交付。**有效用户回合标识 MUST 作为独立任务字段持久化**（进入事件、投影与恢复链，不依赖任何瞬态字段），其维护 MUST 限定于「验收模式非 off 且任务存在检查声明」的任务——未启用验收的任务事件流 MUST 完全不变；首次启用（含运行中切换模式或补挂声明）时 MUST 先以记忆视图重算值初始化标识并落盘，完成前不进行该任务的验收判定。用户消息落库、HITL 回复落库、撤销/弃轮重算时更新标识；用户经真实消息入口追加要求、重答或撤销回合后，即使输出与任务原始 prompt/inputs 完全相同，旧结论也 MUST 失效。**恢复期 MUST 对账**：重建后、该任务任何验收判定前，从记忆视图重算应有标识并与持久化值比对，不一致 MUST 幂等补齐事件，补齐完成前 MUST NOT 进行验收判定。无输入变化时重启前后该标识与指纹 MUST 保持不变。

#### Scenario: 检查器异常判未验证
- **WHEN** 必需检查器执行中抛出异常或超时
- **THEN** 验收状态为 unverified，附带检查器故障记录，不判 passed

#### Scenario: 提示性检查不阻塞
- **WHEN** 任务声明的检查中含提示性检查且其失败
- **THEN** 交付照常进行，提示性发现随交付记录一并保存

#### Scenario: 未启用验收的任务不产生输入标识事件
- **WHEN** 任务无检查声明、或会话验收模式为 off，用户消息正常落库
- **THEN** 不产生任何输入标识事件，事件流与改造前完全一致

#### Scenario: 首次启用时以重算值初始化
- **WHEN** 任务在无检查声明状态下已积累多轮用户消息，随后补挂声明并启用 required 模式
- **THEN** 验收判定前，标识以记忆视图重算的当前有效回合初始化并落盘

#### Scenario: 用户经真实入口追加修改使旧结论失效
- **WHEN** 任务在上一候选验收通过后，用户经消息注入入口（send_message 或 HITL 回复）追加新要求并重跑生成，新输出与旧输出完全相同
- **THEN** 旧 passed 记录因输入快照标识（有效用户回合标识）变化而失效，交付前必须重新检查

#### Scenario: 消息已落库、输入事件未落库的恢复对账
- **WHEN** 用户回合已写入记忆、TASK_INPUT_ADVANCED 尚未落盘时进程崩溃，随后恢复
- **THEN** 恢复对账幂等补齐标识为新回合，旧 passed 记录失效；补齐完成前该任务不进行验收判定

#### Scenario: 撤销已完成、回退事件未落库的恢复对账
- **WHEN** 回合折叠已完成、标识回退事件尚未落盘时进程崩溃，随后恢复
- **THEN** 恢复对账将标识回退为最新存活回合，指纹反映撤销后的有效输入

#### Scenario: 无输入变化的重启指纹不变
- **WHEN** 任务在两次验收之间没有新的用户回合，进程重启后恢复并重新计算输入快照标识
- **THEN** 有效用户回合标识与输入快照标识与重启前一致（不因恢复退化为缺省哨兵）

#### Scenario: 新增输入后重启仍能识别变化
- **WHEN** 用户经消息注入入口追加新要求后进程崩溃，恢复后重新生成出与先前完全相同的输出
- **THEN** 恢复出的有效用户回合标识反映新增回合，旧 passed 记录失效

#### Scenario: 声明变化使旧结论失效
- **WHEN** 任务检查声明的版本指纹变化（增删检查器、改参数或检查器版本升级）
- **THEN** 旧验收记录对新声明无效

### Requirement: 验收记录持久化与恢复可审计

每次检查 MUST 产生持久化验收记录，至少包含：输出指纹、**输入快照标识**、**检查声明版本**、检查器 id 与版本、结论、结构化缺口、**候选引用**（小候选随事件直存、超限外存可解引用）。记录 MUST 进入事件流并折叠进任务投影，崩溃恢复后仍可审计，且失败候选 MUST 可按引用取回。经 `next_step_hint` 投递的缺口提示保持其一次性瞬态语义；待修正事实 MUST 另行随事件持久化，恢复后 MUST 能重建缺口上下文。

#### Scenario: 重启后验收历史可审计
- **WHEN** 含多条验收记录的会话经重启回放重建
- **THEN** 每条记录的结论、缺口、绑定三元组与检查器版本仍可从投影读出

#### Scenario: 重启后取回失败候选
- **WHEN** 一条 failed 验收记录的候选超过直存上限而外存
- **THEN** 恢复后按候选引用可完整取回该候选正文

#### Scenario: 恢复后缺口上下文重建
- **WHEN** 任务在修正轮中途中断，恢复后续跑
- **THEN** 上一轮的持久化缺口被重建并注入续跑上下文

### Requirement: 成本归集与模式行为矩阵

修正轮、检查触发的任何模型调用 MUST 归集到所属任务的成本口径（含失败与后台请求），与现有执行预算共用同一预算判定；检查器 CPU/存储等宿主成本不进入模型 token 口径但 MUST 在验收矩阵中单列。验收能力 MUST 支持影子模式，行为矩阵如下且 MUST 逐格成立：off 模式（无论何种声明）与任何模式下**未声明任何检查**的任务为完全零变化；shadow 模式执行并记录全部声明检查但**不改变交付决策**（必需失败也不重排不修正）；required 模式对必需检查执行门禁（失败→缺口/修正/失败终态），对提示性检查仅记录不阻塞。

#### Scenario: 影子模式不改变交付
- **WHEN** 会话以影子模式配置验收、某任务必需检查失败
- **THEN** 检查结论与缺口照常记录，但交付决策、重排与修正与 off 模式完全一致

#### Scenario: off 模式下声明不产生任何副作用
- **WHEN** 任务携带检查声明但验收模式为 off
- **THEN** 检查不执行、无验收事件、成本零变化

#### Scenario: 修正调用计入任务成本
- **WHEN** 一次修正消耗模型调用
- **THEN** 该调用的用量进入任务成本累计并受预算约束，预算耗尽时后续修正被拒绝
