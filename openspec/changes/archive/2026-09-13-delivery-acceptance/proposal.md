# Proposal: delivery-acceptance

## Why

演进方案（docs/plans/2026-09-12-task-evolution-evidence-design.md §5.1）与两轮真模型实验共同确立：执行结束与结构合格都不代表业务正确——冻结 18 份答复中结构门放行 8 份业务错误；独立留出集 30 输入上结构门放行 15 份错误（52%）。而"确定性业务验证 + 结构化缺口反馈 + 一次受控修正"在同一批输入上把完整交付正确率从 14/30 提到 30/30、错误放行降为 0、每份正确交付成本降 53%（docs/plans/2026-09-12-evolution-design-validation-report.md）。该策略已满足方案 §6 放量规则中"已验证收益"的标准，需要接入生产内核：当前内核没有任何业务级验收挂点，`FINISHED` 一旦落定即无法区分"执行完"与"交付对"。

## What Changes

- **宿主注册验收检查器**：同步纯函数检查器按 id 注册（内核提供协议与流程挂点，不内置任何领域规则）；任务在派发时声明必需检查（检查器 id + 参数 + 必需性），随 TASK_CREATED 持久化。
- **候选-提交分离**：验收模式为 required 时，携带必需检查的任务在成功提交前必经验收边界——先结构检查、后领域检查；以任务收尾为形态的全部成功提交路径（`finish_task` 收尾、observe 判成功的收尾 run、子任务结果上抛、`run_single_task` 兼容入口的内联修正）无一绕过；交互任务的中间交流回合（park 让位）不属交付候选。
- **结构化缺口 + 一次受控修正**：检查失败产出结构化缺口事实（失败条件、涉及字段/记录、依据引用、可修正建议）；预算允许且确为答复错误时最多一次修正，修正后**重跑全部必需检查**。重复缺口、预算不足或检查器故障时终止自动修正，保留候选与未解决项。
- **验收状态独立于执行状态**：`passed / failed / unverified` 三态验收记录随事件持久化（输出指纹、输入修订、检查器版本、结论、缺口）；Task.status 语义不变；检查器异常或未覆盖不得判 passed。
- **成本归集**：修正与检查相关模型调用计入任务成本，受现有执行预算约束。
- 未声明任何检查的任务、以及验收模式为 off 的会话，零行为变化（opt-in，同 execution-limits 先例）；shadow 模式记录结论但不改变交付决策。

## Capabilities

### New Capabilities

- `delivery-acceptance`: 交付验收闭环——宿主检查器注册与任务级声明、候选-提交分离边界、结构化缺口与一次受控修正、独立验收状态与持久化、成本归集。

### Modified Capabilities

（无——验收是任务语义之上的新关注面；task-handoff 的 inputs/依赖条件/id 配对要求不受影响，新声明字段与验收事件为纯新增。）

## Impact

- **交付边界**：`core/loop/steps/finalize.py`（验收挂点、候选形成与成功提交的分离）——需枚举全部成功提交路径确保无一绕过（方案 §5.1 接入边界）。
- **任务模型与投影**：`core/models/task.py`（验收声明 + 修正预算字段）、TASK_CREATED payload、reducers/converters/TaskView、快照序列化。
- **缺口投递**：`next_step_hint` 通道投递一次性缺口提示（现有瞬态语义保留），修正事实另行持久化（新事件 + 投影），恢复时重建。
- **控制工具**：`delegate_task`/`delegate_plan`/入口任务声明必需检查的参数面。
- **预算**：`ExecutionBudget` 复用（活动时间/轮次），修正调用计入任务成本口径。
- **回归资产**：冻结 18 答复重放（10 正确不受影响 / 8 错误全拦）与留出集样例作为验收矩阵锚点（方案 §5.1 验收条款）。
